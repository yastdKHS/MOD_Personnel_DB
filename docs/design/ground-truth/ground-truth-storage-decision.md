## 1. Gate 1-Aとの接続

Gate 1-Aの結論候補(未承認)は「(i)位置参照+(ii)構造的判定ラベルを基本とし、(iii)抽出値
そのものは原則不要」であった。この結論候補が承認された場合、格納方式の評価における
「個人データリスク」の重みは、既存の`ground-truth-storage-method-comparison.md`での評価より
**軽減される可能性がある**(実値を含まないラベルは、CLAUDE.md禁止事項の直接の対象になりにくいため)。

ただし、Gate 1-A §2.3(CategoryD 1:N/N:1)で留保した「一部エッジケースで(iii)相当の情報が
必要になるかもしれない」という未確定要素があるため、**格納方式の検討では、(iii)を一切含まない
前提と、部分的に含む前提の両方を想定しておく必要がある**。

## 2. 追加評価軸での4方式比較

`ground-truth-storage-method-comparison.md`で既に評価した10軸(CLAUDE.md/AGENTS.md/ADR-0008/
Constitution §4/tests/golden整合性/再現性/監査可能性/個人データリスク/引継ぎ容易性/
Resolver validation利用可能性)に加え、今回指示された3軸を追加評価する。

### 2.1 CI/testとの統合可能性

| 方式 | 評価 |
|---|---|
| 方式1(Git管理) | 最も統合しやすい。CIがリポジトリをcheckoutすれば即座にGround Truthへ
  アクセス可能で、追加のsecrets管理・外部アクセス設定が不要 |
| 方式2(Git外+manifest) | 統合には追加設計が必要。CI環境から実データストレージへの
  アクセス経路(認証・ネットワーク到達性)を別途用意する必要がある。CI上でGround Truth
  検証を行う場合、実データ取得のステップがCIパイプラインに追加され、外部ストレージの
  可用性に依存するようになる |
| 方式3(Gold DB経由) | 既存のDBアクセス経路(Repository層)をCIでも再利用できる可能性が
  あるが、CI環境用のDBスナップショット・テストDB分離の設計が別途必要になりうる |
| 方式4(合成データ+別管理) | 合成データ部分はCIに直接統合しやすい(方式1と同等)。
  実データ部分は組み合わせる方式(2または3)のCI統合課題をそのまま引き継ぐ |

### 2.2 実データへのアクセス管理

| 方式 | 評価 |
|---|---|
| 方式1 | リポジトリへのアクセス権がそのままGround Truthへのアクセス権になる。
  個人データを含む場合、リポジトリの閲覧者全員(フォーク・クローンした全員を含む)が
  アクセス可能になり、アクセス制御の粒度が粗い |
| 方式2 | 実データストレージ側で独立したアクセス制御を設計できる(リポジトリの閲覧権限とは
  分離可能)。ただし、この独立したアクセス制御自体を新規に設計・運用する必要がある
  (現時点で未設計) |
| 方式3 | 既存のGold DBアクセス経路(想定されるRepository層・将来のReview UI等)の
  アクセス制御をそのまま利用できる可能性があるが、Gold DB自体が「防衛省公表情報」を
  対象とした設計であり、Ground Truth固有のアクセス制御要件(例: 意図的に難しいケースを
  含むため、限定公開が望ましい可能性)との整合は別途検討が必要 |
| 方式4 | 合成データ部分はアクセス制御の必要性が低い(個人データを含まないため)。
  実データ部分は組み合わせる方式の課題をそのまま引き継ぐ |

### 2.3 将来の設計変更への柔軟性

| 方式 | 評価 |
|---|---|
| 方式1 | ラベルスキーマの変更はGit管理下で追跡しやすいが、大量データをリポジトリで
  バージョン管理し続けると、リポジトリサイズの肥大化・historyの複雑化を招きやすく、
  将来的な変更(スキーマ移行等)のコストが増大するリスクがある |
| 方式2 | manifestの変更はGitで柔軟に追跡できる。実データ自体のスキーマ変更は、
  Git外ストレージの設計に依存するため、ストレージ側の柔軟性(スキーマレス形式か、
  厳格なスキーマかなど)を別途検討する必要がある |
| 方式3 | DBスキーマ変更は、既存の`docs/database/schema.md`のようなmigration管理の
  対象になり、ADR起票プロセスを伴う可能性がある(変更コストは高いが、変更履歴の
  厳密な管理という点では堅牢) |
| 方式4 | 合成データのスキーマ変更は容易(方式1相当)。実データ部分は組み合わせる方式に依存 |

## 3. 「格納場所」と「副次的な設計項目」の分離

**重要**: 「Git外に置く」という決定は、それ自体では格納方式の設計として不十分である。
以下の副次的な設計項目は、格納場所の選択(方式1〜4のいずれか)とは**別問題**として、
格納場所が決定した**後に**個別に設計する必要がある。**本Task(Gate 1-B)では、これらの
項目を実際に設計・決定しない。項目の存在と、格納場所決定への依存関係のみを整理する。**

| 副次的設計項目 | 内容 | 格納場所決定への依存 |
|---|---|---|
| 実データの保存先(具体的な物理/論理ロケーション) | 方式2の場合、`/data/`(既存
  `.gitignore`パターン)を使うか、別の新規ロケーションを使うか | 方式2選択後に決定 |
| 永続性 | セッション・コンテナの再作成をまたいで消失しないか(本セッションが過去に
  経験した`/tmp`データ消失と同種のリスクへの対策) | 方式2・4(実データ部分)選択後に決定。
  方式1・3はGit/DBの既存の永続化機構に乗るため、この項目の設計コストが相対的に低い |
| バックアップ | 実データストレージのバックアップ方針 | 方式2選択後に決定。方式1・3は
  リポジトリ/DBの既存バックアップ運用に乗る可能性がある(ただし現状のDB/リポジトリの
  バックアップ運用自体が本セッションで確認されていない点に留意) |
| 識別子(ID体系) | PDF・Section・Block・ラベルをどう一意に識別するか | 方式によらず
  共通で必要(方式1〜4いずれでも識別子設計は不可避) |
| manifest | どのPDF・どのSectionが対象で、それぞれのラベルがどこにあるかの目録 |
  方式2で特に重要(Gitにはmanifestのみを置く設計のため)。方式1・3でも目録的な情報は
  有用だが、必須度は方式2より低い |
| versioning | ラベルの改訂履歴をどう管理するか | 方式1はGit履歴で自然に得られる。
  方式2はmanifestの変更をGit履歴で追える一方、実データ自体のversioningは別途必要。
  方式3はDBのmigration/バージョン管理機構に依存 |
| checksum/hash | 実データの改ざん・破損検出 | 方式2で特に重要(Git外データの完全性を
  Git側から検証する手段として)。方式1はGit自体が内容ハッシュを保持するため、この項目は
  Gitの既存機能でおおむね代替できる |
| access control | 2.2で既述 | 方式2・3で個別設計が必要。方式1はリポジトリのアクセス権に
  一任される |
| 再現性 | 同じ入力から同じGround Truthが得られる保証 | ラベリングプロセス(Gate 1-Cの
  範囲)に強く依存し、格納方式そのものとは別軸の問題 |
| データが消失した場合の検出 | 永続性の裏返しとして、消失をどう検知するか(定期的な
  checksum照合等) | 方式2で特に重要 |

**この分離を明示する理由**: 前回の`ground-truth-storage-method-comparison.md`の推奨
(方式2を有力候補とする旨)は、格納**場所**の議論としては妥当な可能性があるが、
上記副次的設計項目(特に永続性・バックアップ)を未設計のまま方式2を「確定」させると、
本セッションが過去に経験した`/tmp`データ消失(Task-E15での復旧作業を要した事例)と
同種のリスクを、Ground Truthについても抱えることになる。**したがって、方式2を選ぶ場合、
副次的設計項目(特に永続性)の設計が伴わない限り、格納方式の決定を完了したとは扱わない。**

## 4. Gate 1-B 結論候補(未確定、承認前)

**結論候補**:

1. Gate 1-Aの結論候補(「(i)+(ii)を基本とし(iii)は原則不要」)が承認される場合、
   個人データリスクの観点では方式1(Git管理)の相対的な不利さがやや軽減されるが、
   `ground-truth-storage-method-comparison.md`で確認した既存の2先例
   (`.gitignore`の`/data/`パターン、`pdfs.file_path`の外部参照設計)との整合性の観点では、
   引き続き方式2が最も既存アーキテクチャに整合する。
2. ただし、方式2を選ぶ場合、**「Git外に置く」という決定だけでは不十分**であり、
   上記3章の副次的設計項目(特に永続性・バックアップ・checksum)を別途具体的に設計する
   必要がある。**この設計自体は本Task(Gate 1-B)の範囲外とし、方式2が承認された場合の
   次Task候補として扱う。**
3. CI/test統合可能性の観点では方式1が優位だが、Gate 1-Aの結論候補どおり(iii)を
   含まない場合、Ground Truthのデータ量・個人データ非含有という性質から、方式2でも
   CI統合の追加コストは限定的である可能性がある(未検証)。

**いずれも結論候補であり、`Status: APPROVED`ではない。**
